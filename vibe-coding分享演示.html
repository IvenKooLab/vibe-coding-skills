一、背景:站在公司验证过的路上,做产品化

公司内部已经有多套 AI 编码方法论的实践。其中 superspecflow 用 OpenSpec + Superpowers 验证了一条很扎实的路:规格契约驱动 + 标准化方法论。这条路是对的——本室的 vibe-coding 在这条路上继续做产品化:把同样的 OpenSpec 规格契约、同样的 Superpowers 方法论,打包成可移植的标准包,并补全了精简纪律、需求盘问、工程框架、跨会话记忆等能力。

superspecflow 验证的核心结构

组件定位产物命令
OpenSpec项目的"宪法"——规格契约,所有需求/设计沉淀进仓库 specproposal / design / specs / tasks 四件套/propose
SuperpowersAI 的"技能包"——标准化的子 Skill 集(澄清/计划/TDD/调试/验证)按计划执行 + 完成前验证/apply
归档收尾交付前的质检——把变更回写进主规格归档的 change + 更新后的 specs/archive

vibe-coding 做的产品化:在这条路上补什么

vibe-coding 完全包含 superspecflow 的核心能力(openspec 包 = 规格契约,superpowers 包 = 方法论纪律),并额外补了四个维度,让这套能力覆盖从"一个字段的改动"到"跨团队的契约变更"全场景:

维度superspecflow 已有vibe-coding 补的
规格契约OpenSpec proposal/specs/design/tasksopenspec 包,同源能力,跨工具字节同构
方法论纪律Superpowers 5 skill(brainstorming/TDD/...)superpowers 包,5 纪律合并为单文件
需求盘问—grill-me——动手前对计划做无情盘问,逐枝走完决策树
精简纪律—ponytail——能不写就不写,代码量均值 -54%
工程框架—Trellis——spec/task/memory 持久化 + 多 agent 协作
统一入口三个独立命令vibe——/vibe 弹菜单按需路由,记一个命令就够
一句话:vibe-coding 不是另起炉灶,是把公司验证过的路产品化——同样的规格契约 + 方法论纪律,加上需求盘问 / 精简纪律 / 工程框架 / 统一入口,形成一套可移植、跨工具通吃、从轻到重全覆盖的完整体系。重项目走完整规格流程,轻项目随取随用,同一套体系。

三、vibe-coding 的四个增量设计点

在规格契约 + 方法论纪律这个已验证的底座之上,vibe-coding 补了四个设计点,让这套能力覆盖从单字段改动到跨团队契约变更的全场景。每个点都对应一个真实痛点。

增量 ①:统一入口 —— /vibe 路由器

解决的痛点
多包在手,记不住什么时候用哪个。新手面对 6 个包会迷茫。
设计
/vibe 弹两段式菜单:先选 4 大类(动手前/规格契约/写码时/跨会话),再选具体包。
效果
记一个 /vibe 就够;指名调用(/openspec 等)可跳过菜单。新手友好,老手直接。

增量 ②:需求盘问 —— grill-me

解决的痛点
计划看起来"差不多对了",但藏着没拍板的决策,动手后才发现。
设计
对计划做无情盘问,一次问一个问题,带推荐答案,逐枝走完决策树。
效果
动手前把软肋逼出来,避免返工。和 superpowers 的 brainstorming 互补——前者单点深挖,后者完整流程开场。

增量 ③:精简纪律 —— ponytail

解决的痛点
AI 容易过度设计:引新依赖、写投机抽象、加包装组件。token 和维护成本高。
设计
"梯子":YAGNI → 复用 → stdlib → 原生 → 已装依赖 → 一行 → 最小代码。动手前从上往下找第一个成立的横档。
效果
上游实测:代码量均值 -54%(成本 -20%、速度 -27%),安全护栏 100% 保留。懒的是解法,绝不懒于读代码。

增量 ④:跨会话记忆 —— Trellis + 可移植打包

解决的痛点
AI 每个会话从零开始,不记得项目约定;方法论语料跨工具要维护多份。
设计
Trellis 把 spec/task/memory 持久化进仓库;全部六包字节同构,一份 SKILL.md 在 Claude Code / Qoder / Trae 三处直接 cp 生效。
效果
跨会话有记忆 + 多 agent 协作;维护一份源分发到各工具,团队混用工具也统一。蒸馏不搬源码,License 干净(MIT 为主)。
一句话总结:规格契约 + 方法论纪律(已验证的底座)+ 统一入口 + 需求盘问 + 精简纪律 + 跨会话记忆 = 一套完整体系。重项目叠加 OpenSpec 完整流程走规格驱动(同源于 superspecflow),轻项目用 grill-me+ponytail 做日常,各取所需。

五、日常实践分享

方法论之外,再分享两个日常在用的实践——一个是我造的轮子(nacos2-mcp),一个是我在用的笔记工具(Obsidian 模板)。都是小东西,但切实解决了手头的问题。

实践一:nacos2-mcp —— 让 AI 读得到配置

现象:同一个逻辑,AI 反复写、反复错。 根因:这些逻辑其实写在 nacos 配置上,但 AI 读不到 nacos 的内容,只能凭代码猜——猜错了就重写。
环节说明
查方案官方开源的 nacos-mcp 只支持 nacos 3.0+,但我们部门用的是 Nacos 2.3.2 —— 官方版用不了。
造轮子改了一个 nacos2-mcp 出来,兼容 2.x,供科室共用。具体用法见仓库内 README。
使用方式把本工程的 dataId 和 group 发给 mcp 即可,AI 自动读到配置内容,不用手动复制粘贴。
效果AI 能读全配置 → 不再凭空猜 → 重复写代码的问题从根上缓解。
git 地址:http://git.sinosafe.com.cn/marketing_customer_service/mcp.git(与 vibe-coding 同级,都是科室 AI 分享仓库)

实践二:Obsidian + Templater —— 笔记提效

日常的会话纪要、需求笔记、踩坑记录,我都放 Obsidian。核心提效点是 Templater 插件——预设好模板,一键生成结构固定的笔记,不用每次从空白文档开始想格式。

模板类型模板内容解决什么
会话纪要日期/参会人/议题/决议/待办(带负责人和截止)会一开完,5 秒生成结构化纪要,不用事后补格式
需求笔记需求标题/背景/验收标准/影响范围/关联系统接需求时按固定结构记录,后面喂给 AI 做上下文也方便
踩坑记录问题/根因/解决/预防/复现步骤bug 改完顺手记一条,下次遇到同类问题能翻出来
技术调研问题/候选方案/对比维度/结论/参考链接技术选型时有固定 checklist,不会漏维度
为什么分享这个:笔记工具大家都在用,但很多人是"建个空文档就开始写"。Templater 的价值是把重复的结构劳动固化下来——和 vibe-coding 蒸馏方法论是同一个思路:把好的东西沉淀成可复用的模板,下次直接套。
Obsidian 的安装和 Templater 配置网上教程很多,这里不展开;想看我那套模板的话可以会后找我拿。重点是思路:固定模板 + 一键生成,日常记录效率显著提升。

六、怎么用:安装与上手

vibe-coding 的安装刻意做得很轻——没有重型 install 脚本,六个包全部手动 cp 即可。符合 ponytail"能不写就不写"的精神。
1clone 仓库
git clone http://git.sinosafe.com.cn/marketing_customer_service/vibe-coding.git
2按工具 cp 到对应目录——一份 SKILL.md,三处生效(字节同构):
工具skills 落点命令落点
Claude Code(全局)~/.claude/skills/<包名>/SKILL.md~/.claude/commands/vibe.md
Qoder(项目)<项目>/.qoder/skills/<包名>/SKILL.mdQoder 在 rule 层配
Trae(项目)<项目>/.trae/skills/<包名>/SKILL.md同上
六个包全部手动 cp,无脚本依赖——最省心,也最符合"能不写就不写"。
3说 /vibe 开始
一句话口诀:装好说 /vibe,记一个命令就够。拿不准用哪个包 → /vibe 弹菜单;清楚用哪个 → 直接 /grill-me、/ponytail 等指名调用,跳过菜单。

七、总结与展望

三句话总结

  1. vibe-coding 把公司验证过的规格驱动路线产品化了。含 OpenSpec 规格契约 + Superpowers 方法论纪律(同源于 superspecflow 验证的能力)+ Trellis 工程框架,打包成可移植标准包。重项目走完整规格流程,轻项目随取随用。
  2. 六大包各管一段,/vibe 做总入口。规格契约/方法论/工程框架是重型底座,叠加需求盘问(grill-me)、精简纪律(ponytail)、统一入口(vibe)三个增量,覆盖全场景。
  3. 蒸馏不搬运,跨工具通吃。MIT 为主,一份 SKILL.md 三处生效(Claude Code/Qoder/Trae),任何项目都能装。
