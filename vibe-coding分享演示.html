一、背景:superspecflow 与 vibe-coding 是两种风格

公司内部已经有多套 AI 编码方法论的实践。superspecflow 是其中一种:用 OpenSpec 做"项目的宪法",用 Superpowers 做"AI 的技能包",三阶段命令对应开发流程。vibe-coding 是另一种风格,放一起对照看,各有适用场景。

superspecflow 的核心结构

组件定位产物命令
OpenSpec项目的"宪法"——规格契约,所有需求/设计沉淀进仓库 specproposal / design / specs / tasks 四件套/propose
SuperpowersAI 的"技能包"——标准化的子 Skill 集(澄清/计划/TDD/调试/验证)按计划执行 + 完成前验证/apply
归档收尾交付前的质检——把变更回写进主规格归档的 change + 更新后的 specs/archive

两种风格,各有适用场景

听完他们的分享,我做 vibe-coding 时走了另一条路——不是替代,是另一种取舍。两者适合不同场景:

维度superspecflow(理赔)vibe-coding(本室)
定位重型、流程化、契约驱动轻量、按需、可移植
适合项目中大型跨会话、多 agent、需要需求契约留痕轻量/中单人、多项目复用、跨工具混用
流程颗粒度三阶段全流程,每步暂停确认/vibe 按需路由,想用哪步用哪步
跨工具脚本适配器生成字节同构(一份 SKILL.md 三处生效)
学习成本需理解 OpenSpec + Superpowers + 三命令记一个 /vibe 就够
典型场景新需求走完整 propose→apply→archive改 bug → /grill-me;嫌啰嗦 → /ponytail
一句话:superspecflow 像正规军重装师(流程严谨、契约留痕),vibe-coding 像特种兵小队(轻便灵活、随取随用)。选哪种,看你的项目规模和协作方式。重型项目完全可以两者叠加——用 OpenSpec 定契约,用 vibe-coding 的轻量包做日常。

二、vibe-coding 的解法:六个包

vibe-coding 不是 superspecflow 的替代,是另一种风格——把业界优秀的方法论(skill)蒸馏成一套标准包,任何项目、任何工具(Claude Code / Qoder / Trae)装上即用。

三、设计取舍:两种风格背后的选择

没有完美方案,只有不同取舍。这一节把两种风格在关键决策点的差异摆出来,方便大家对照自己的项目选。

取舍 ①:流程颗粒度

superspecflow 选了
三阶段全流程,每步暂停确认。换来了:流程严谨、契约留痕、可追溯。
vibe-coding 选了
/vibe 按需路由,想用哪步用哪步。换来了:轻量、快速、小改动成本低。
各自的代价
前者对熟练开发者有摩擦;后者缺少强制的全流程兜底,靠开发者自觉。明文规则:轻量项目可只用方法论层,不引入 OpenSpec。

取舍 ②:跨工具适配方式

superspecflow 选了
脚本"适配器"按工具生成不同格式。换来了:能针对每个工具做精细优化。
vibe-coding 选了
字节同构:同一份 SKILL.md,Claude Code / Qoder / Trae 直接 cp 生效。换来了:维护一份源,零转换成本。
各自的代价
前者维护脚本本身有成本;后者放弃了对单个工具的精细定制,换 IDE 不换 skill。

取舍 ③:产出代码量

superspecflow 选了
跑完整 brainstorming + writing-plans + TDD + code-review。换来了:质量把关环节多、覆盖全。
vibe-coding 选了
叠加 ponytail 的"梯子":YAGNI → 复用 → stdlib → 原生 → 一行 → 最小代码。换来了:代码量显著下降。
各自的代价
前者 token 和时间成本高;后者精简可能漏掉一些"本该有"的环节(靠其他包补回)。上游实测:ponytail 代码量均值 -54%(成本 -20%、速度 -27%)。

取舍 ④:协议策略

superspecflow 选了
直接用上游完整 harness(npm install)。换来了:功能完整、自动化程度高。
vibe-coding 选了
蒸馏而非搬运:只取方法论 + 中文说明,不搬源码。
各自的代价
前者需遵守上游协议(如 AGPL 有传染性);后者协议干净(MIT 为主),但放弃了一些上游自动化能力。真正"硬"的约束都留给项目自己的 hook/CI。
一句话总结:两者是同一片光谱的两端——superspecflow 重型严谨,vibe-coding 轻量灵活。选哪种取决于项目规模和团队协作方式;中型以上项目完全可以两者叠加(用 OpenSpec 定契约 + 用 vibe-coding 的轻量包做日常)。

五、日常实践分享

方法论之外,再分享两个日常在用的实践——一个是我造的轮子(nacos2-mcp),一个是我在用的笔记工具(Obsidian 模板)。都是小东西,但切实解决了手头的问题。

实践一:nacos2-mcp —— 让 AI 读得到配置

现象:同一个逻辑,AI 反复写、反复错。 根因:这些逻辑其实写在 nacos 配置上,但 AI 读不到 nacos 的内容,只能凭代码猜——猜错了就重写。
环节说明
查方案官方开源的 nacos-mcp 只支持 nacos 3.0+,但我们部门用的是 Nacos 2.3.2 —— 官方版用不了。
造轮子改了一个 nacos2-mcp 出来,兼容 2.x,供科室共用。具体用法见仓库内 README。
使用方式把本工程的 dataId 和 group 发给 mcp 即可,AI 自动读到配置内容,不用手动复制粘贴。
效果AI 能读全配置 → 不再凭空猜 → 重复写代码的问题从根上缓解。
git 地址:http://git.sinosafe.com.cn/marketing_customer_service/mcp.git(与 vibe-coding 同级,都是科室 AI 分享仓库)

实践二:Obsidian + Templater —— 笔记提效

日常的会话纪要、需求笔记、踩坑记录,我都放 Obsidian。核心提效点是 Templater 插件——预设好模板,一键生成结构固定的笔记,不用每次从空白文档开始想格式。

模板类型模板内容解决什么
会话纪要日期/参会人/议题/决议/待办(带负责人和截止)会一开完,5 秒生成结构化纪要,不用事后补格式
需求笔记需求标题/背景/验收标准/影响范围/关联系统接需求时按固定结构记录,后面喂给 AI 做上下文也方便
踩坑记录问题/根因/解决/预防/复现步骤bug 改完顺手记一条,下次遇到同类问题能翻出来
技术调研问题/候选方案/对比维度/结论/参考链接技术选型时有固定 checklist,不会漏维度
为什么分享这个:笔记工具大家都在用,但很多人是"建个空文档就开始写"。Templater 的价值是把重复的结构劳动固化下来——和 vibe-coding 蒸馏方法论是同一个思路:把好的东西沉淀成可复用的模板,下次直接套。
Obsidian 的安装和 Templater 配置网上教程很多,这里不展开;想看我那套模板的话可以会后找我拿。重点是思路:固定模板 + 一键生成,日常记录效率显著提升。

六、怎么用:安装与上手

vibe-coding 的安装刻意做得很轻——没有重型 install 脚本,六个包全部手动 cp 即可。符合 ponytail"能不写就不写"的精神。
1clone 仓库
git clone http://git.sinosafe.com.cn/marketing_customer_service/vibe-coding.git
2按工具 cp 到对应目录——一份 SKILL.md,三处生效(字节同构):
工具skills 落点命令落点
Claude Code(全局)~/.claude/skills/<包名>/SKILL.md~/.claude/commands/vibe.md
Qoder(项目)<项目>/.qoder/skills/<包名>/SKILL.mdQoder 在 rule 层配
Trae(项目)<项目>/.trae/skills/<包名>/SKILL.md同上
六个包全部手动 cp,无脚本依赖——最省心,也最符合"能不写就不写"。
3说 /vibe 开始
一句话口诀:装好说 /vibe,记一个命令就够。拿不准用哪个包 → /vibe 弹菜单;清楚用哪个 → 直接 /grill-me、/ponytail 等指名调用,跳过菜单。

七、总结与展望

三句话总结

  1. vibe-coding 是 superspecflow 的"另一种风格"——不是替代关系,是同一光谱的两端。重项目可以叠加(OpenSpec 定契约 + vibe-coding 做日常),轻项目单独用 vibe-coding 就够。
  2. 六个包各管一段,/vibe 做总入口。从"动手前"到"完成前验证"到"跨会话记忆",每段都有专人;记不住用哪个时,/vibe 弹菜单帮你选。
  3. 蒸馏不搬运,跨工具通吃。MIT 为主,一份 SKILL.md 三处生效,任何项目都能装。

展望:下一步可能的方向

  • 补一个"标准/约束层"包——跨项目通用的工程约束(代码生成前必读文件、禁 dry-run、commit/分支规范),和 superspecflow 的重型流程互补。
  • 通用 code-review 包——目前审查视角只有 ponytail 的"精简",可补安全/性能/正确性多视角。
  • Hook 机械拦截指导——把"软约束"和"硬约束"分层,真正需要 100% 强制的场景教项目怎么落地到 hook/CI。
