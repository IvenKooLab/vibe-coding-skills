# Superpowers 在我司怎么落地 —— 开发人员实操指南

> 写给一线开发同学:这套东西是什么、为什么推、你日常怎么用、怎么避坑。看完就能上手。

---

## 一、这东西是什么?一句话讲清

Superpowers 不是某个框架或工具,而是一套**让 AI 写代码时"按规矩干活"的工作方法**。它由几个 skill(技能文件)组成,装进你的 AI 编程工具(Claude Code 或 Qoder)后,AI 就会在该提问时提问、该写测试时写测试、该验证时验证,而不是闷头一顿乱写。

> 类比:没装 Superpowers 的 AI,像个"接到活就开干、不问需求"的实习生;装上之后,像有个"先问清楚、再动手、做完自检"的靠谱同事。

我们这次要推的,就是把这套方法装进大家的日常开发工具,让 AI 输出的代码**质量稳定、可追溯、少返工**。

---

## 二、为什么要推?(解决什么真实痛点)

- AI 直接写代码,经常**需求没问清就动手**,做完发现方向错了,返工。
- AI 写的代码**没测试、没边界处理**,一上测试 / 生产环境就出问题。
- 多人用 AI,**每个人让 AI 干活的方式不一样**,产出质量参差不齐。
- 出了 bug,靠**"改改试试"碰运气**,改了 A 坏了 B,定位半天。

Superpowers 用一套固定流程把这些坑堵上:**动手前先澄清 → 拆成小任务 → 先写测试再写码 → 系统化调试 → 完成前先验证**。

## 三、一张图看懂:它和我司已有的东西什么关系?

我司技术体系里,有三层东西配合使用,各管一摊、不重叠:

| 层 | 管什么 | 我司对应 | 举例 |
|---|---|---|---|
| 规格层(OpenSpec) | 做什么、契约、验收、留痕 | 复杂项目按需引入 | 需求提案、接口契约、验收标准,长期归档 |
| 方法论层(Superpowers) | 怎么做、过程管控、质量 | 本次要推的 5 个 skill | 先澄清、拆任务、TDD、调试、验证 |
| 框架知识层(已有) | 用什么、公司技术栈 | lina-* 系列 skill | lina-redis、lina-mybatis-plus 怎么用 |

> 核心原则:**OpenSpec 管"契约与沉淀",Superpowers 管"流程与质量",一件事只由一套主导,互不越界。** 对绝大多数日常开发,你只需要用 Superpowers 这套 skill 就够了。

## 四、5 个核心 skill,日常就这么用

装好之后,这 5 个 skill 会在合适的时机**自动触发**,你不用记命令,但要理解每一步在干嘛:

> 这 5 个 skill 哪来的?**方法论内核取自 superpowers 官方开源项目(github.com/obra/superpowers)**,再结合**我司 Lina 框架**已有的 skill 生态与实际开发场景,做了中文化和本地化裁剪——不是凭空写的,这套方法在业界已大规模验证。它们与 `lina-*` 框架知识 skill 是配合关系:本套管"怎么干",`lina-*` 管"用什么"。

| 顺序 | Skill | 什么时候用 | 产出 |
|---|---|---|---|
| 1 | 需求澄清 brainstorming | 接到"加个功能""改一下"这类需求时 | 澄清后的需求 + 2-3 个方案 + 确认 |
| 2 | 编写计划 writing-plans | 需求确认、准备动手前 | 拆成 2-5 分钟的小任务清单 |
| 3 | 测试驱动 test-driven-development | 写新逻辑、修 bug 时 | 先写的测试 + 最小实现 |
| 4 | 系统化调试 systematic-debugging | 排查 bug、报错、性能问题时 | 根因 + 最小修复 + 防回归测试 |
| 5 | 完成前验证 verification-before-completion | 准备说"做完了"、提交、上线前 | 跑过的构建 / 测试证据 |

> 📎 这 5 个 skill 的完整内容见本文档**文末附件**(双击图标可直接打开取用)。

### 一句话开关:对 agent 说 `/superpowers`

不用记 5 个 skill 的名字和顺序——对 agent 说一句 **`/superpowers`**(Claude Code)或**「启用 superpowers」**(Qoder),它就进入"按方法论干活"模式:**本会话后续每个任务,自动依次走** 澄清需求 → 拆计划 → TDD 实现 → 系统化调试 → 完成前验证。你只管提需求、确认方案、看结果。

> 关掉也简单:说一句"停用 superpowers"即可。涉及公司框架时,agent 会自动配合 `lina-*` skill。

**举例**:你说 `/superpowers`,再发"给用户模块加个批量导出"。agent 会先问你格式 / 数据量 / 权限(澄清)→ 拆成带验证步骤的小任务(计划)→ 先写测试再实现(TDD)→ 完成前跑构建 + 测试给你看(验证)。**全程你不用喊任何 skill 名字。**

> 重点不是"AI 自动跑完全程",而是"每一步都有规矩、有验证、能追溯"。你随时可以打断、纠偏。

### 怎么确认开关真的开了?

敲完 `/superpowers` 后,对照这两点就知道有没有生效:

1. **agent 会回一句确认**,类似:"已启用 superpowers 方法论,后续任务我会按 澄清 → 计划 → TDD → 调试 → 验证 执行"。
2. **你随便发个需求**(如"给用户模块加个导出功能"),它**先提问**(格式?数据量?权限?),而不是直接开始写代码。

> 如果 agent 二话不说直接写码、不提问,说明开关没生效——回看 `/superpowers` 命令是否装上(Claude Code 里敲 `/` 能在列表看到 `superpowers`),或项目引导(`CLAUDE.md` / `.qoder/rules`)是否就位。

## 五、常见踩坑(避开这些)

| 坑 | 正确做法 |
|---|---|
| 需求还没说清就让 AI 开干 | 先用 brainstorming 澄清,确认后再动手 |
| AI 写完直接说"好了",没跑测试 | 必须 verification:跑构建 + 测试,给证据 |
| 修 bug 靠"改改试试" | 用 systematic-debugging:先复现、找根因、再改 |
| 把公司框架用法塞进方法论 skill | 框架知识看 lina-* skill;方法论 skill 只管"怎么干" |
| 复杂项目(支付 / 合规)只用 Superpowers 不留契约 | 这类要 OpenSpec 定基线 + Superpowers 执行,串联用 |

## 六、我司项目怎么选型?

不是所有项目都一样搞法。按复杂度二选一。

### 轻量项目 → 只用 Superpowers(本套 skill)

满足下面任意两条,就只用这套 skill,别上 OpenSpec:

- 单人开发,周期短(≤3 个月),一次性需求
- 功能单一:简单 CRUD、工具脚本、内部小页面
- 无合规审计、无跨团队协作
- 接口少(≤5 个),无复杂事务

举例:运营活动 H5、数据看板小模块、运维自动化脚本、内部后台简单增删改查。

### 复杂项目 → OpenSpec 定契约 + Superpowers 管执行

满足任意一条,就要两套配合(金融 / 合规场景常见):

- 多团队协作、前后端分离、多端互通
- 中台、支付、交易、风控,有分布式事务 / 容灾
- 需合规审计、故障追溯(保险核心业务、资金类)
- 长期维护(≥6 个月),多人接手

举例:理赔核心、收付费链路、保单中台、风控规则引擎。这类项目:OpenSpec 写需求和接口契约(留痕、可审计),Superpowers 负责按契约拆任务、TDD、验证。

> 一句话口诀:**小需求、单人短期 → 单用 Superpowers,轻量快迭代;中台 / 支付 / 合规 / 长期项目 → OpenSpec 定规范,Superpowers 控编码。**

## 七、FAQ

**Q1:这套 skill 会不会让我变慢?**
短期头几个任务可能多几轮对话(因为 AI 会先问)。但换来的是**少返工、少线上事故**,整体是变快的。

**Q2:我已经用得很顺手了,可以不用吗?**
可以局部用。性价比最高的两步建议都留着:**verification(完成前验证)** 和 **brainstorming(动手前澄清)**。

**Q3:skill 里引用的公司框架只有 lina-*,我用别的怎么办?**
方法论 skill 是通用的(管"怎么干");具体框架用法(管"用什么")看对应的知识类 skill。公司自研的知识型 skill 后续会逐步补进交叉引用。

**Q4:在哪看完整规范、想自己写 skill 怎么办?**
团队共享目录里:`docs/skill编写规范.md`(怎么写)、`README.md`(总览)。照着 `_template/SKILL.md` 套就行。
